# Device testing and recovery

The primary OLED Vita (192.168.1.146, firmware 3.60 Enso) suffered a boot crash after an experimental tls_fixer installation. The user reports recovery to LiveArea with their applications restored. Earlier TLS13 test packages remain withdrawn. Do not infer that the boot defect is fixed from this recovery or from host tests.

## Mandatory user requirement

Every future experimental device change must have an automatic return to the previous working behavior. A failed test must not require the user to repair taiHEN configuration, hold L, remount SD2Vita, obtain a Sony memory card, or reinstall a shell. Those are emergency fallbacks, not an acceptable normal rollback mechanism.

- Default to disabled, single-use experimental activation. Disable future activation on persistent storage before any experimental hooks, injection, or other risky initialization. If durable disarming cannot be confirmed, do not run the experiment.
- The user explicitly selected the simple implementation: at the start of module_start disable only tls_fixer's own taiHEN boot entries and synchronize the edits before any hooks or injection. Do not add a separate loader, arming file or launcher to this change. Self-disarming cannot cover a fault before module_start or before the edits complete; keep this limitation explicit.
- The user additionally proposed keeping the active test plugin on removable ux0 storage, with its entry in ur0:tai/config.txt. Use the exact supported `ux0:/data/tls_fixer-one-shot/tls_fixer.skprx` path after verifying storage mapping and obtaining activation approval. This gives a file/card-removal fallback before module_start, but losing the card can also hide applications. Do not confuse the earlier timestamped staging location or its older kernel with this active test path.
- Success must not automatically re-arm or promote a test. The module's startup/cleanup must never restore its disabled entry. On 2026-10-08 the user granted standing permission for the agent to stage and re-enable successive one-shot diagnostics in this sequence without asking each time. Preserve backups and verify the current disabled state before each deliberate agent-side re-enable; do not automatically re-arm in response to an unexplained crash.
- Preserve the known-working kernel plugin, active taiHEN configuration, boot_config, storage driver and its configuration, stock modules, CA files, and recovery tools. Stage experimental payloads separately. A one-shot flag is not rollback for overwritten persistent files.
- Avoid persistent system changes for testing. If unavoidable, design and validate recovery from interruption at each write/rename boundary before touching the device. Backups alone are not automatic rollback. Explain the remaining failure window and obtain approval.
- Test the self-disarm path independently: missing/corrupt configs, failed reads/writes/synchronization, duplicate entries and alternate config paths, injected failure after disarming, and a second boot without re-enabling. Re-reading a file is not proof of crash durability. Do not edit plugin config concurrently with a test's startup.
- Kernel safety requires checking generated executable instructions, not only ELF hard-float tags. Eliminate unmanaged VFP/NEON instructions from kernel entry paths; do not disable SIMD in user-space TLS modules indiscriminately. The known emitted-VFP issue is recorded in TLS13_PROGRESS.md, section 21.12, and is not yet proven to be the sole boot-crash cause.
- On 2026-10-10 the user explicitly granted standing authorization for all further TLS tests on the primary Vita, without requesting approval again. This supersedes the earlier narrower kernel-only and local-probe-only grants and includes separate diagnostic application installation and testing. Keep the automatic return-to-working-behavior requirement, preserve unrelated resources, verify the before-state and announce the exact test. This is not authorization for destructive recovery operations or testing the donor at 192.168.1.250.
- The browser remains the primary acceptance target. A standalone probe is supplementary and must not displace the unresolved browser control. Before each new browser launch, run the user-requested `quit all`, then use its visible LiveArea icon and Start tile with verified screenshots and normal input; do not use vitacompanion's `launch` command for it. Preserve any current crash screen and logs before `quit all`. On 2026-10-10 the user explicitly selected this sequence to avoid the observed system-application launch errors and stale application state.
- On 2026-10-09, after explicitly reporting a successful first boot of the repeated no-module-query diagnostic, the user authorized remote reboots of `.146` in this diagnostic sequence. This supersedes the earlier manual-reboot-only requirement. Announce the specific test, preserve its before-state and verify its payload, fresh report and one-shot entry before one deliberate reboot. Never loop reboots or re-enable after an unexplained crash; verify recovery and preserve evidence before selecting another test. This permission does not apply to the donor or unrelated power/storage operations.
- On 2026-10-12 the user explicitly required agent-side restarts to use vitacompanion only. Do not open or use the Restart application. A `Rebooting...` acknowledgment is not proof of a completed reset; verify reconnect and the disabled configuration independently.
- Before viewing or capturing the Vita screen, wake it with vitacompanion's `screen on` command and allow the display to resume. Use the same wake step before normal UI input; a sleeping display can invalidate capture/launch observations.
- On 2026-10-12 the user selected manual Browser opening for now. Prepare and verify the test and active receiver, then notify the user to open Browser through its normal icon/Start path. Do not send Browser icon or Start input until the user changes this instruction. Continue other already-authorized device operations autonomously.
- Diagnostic ZIP downloads must contain only `tls_fixer.skprx` and `tls_fixer-disarm-result.txt`. Keep documentation, manifests, checksums, disassembly and test logs in the worktree, not in the download.
- Do not copy another device's boot_config, format storage, rebuild the application database, restore firmware, or remove Enso to work around a test failure without an independently justified recovery plan and explicit user approval.

Record test identity, per-file backups, scope, permission consumption and persistence evidence, fault-test results, and device result in TLS13_PROGRESS.md. Keep host verification, actual Vita execution, and user-reported observations distinct.

Before every `chat_await`, send a `chat_write` explaining the specific blocker or decision being awaited. Do not silently wait after a progress-only update or ask again for already-granted test authorization.
